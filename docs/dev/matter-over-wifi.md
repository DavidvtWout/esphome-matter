
The `CONFIG_ENABLE_WIFI_AP` and `CONFIG_ENABLE_WIFI_STATION` Kconfig options control whether connectedhomeip manages the WiFi radio or not. Since the `wifi` component already takes control of the WiFi radio, both options need to be disabled.

However, disabling these options also compiles out all of the services that matter-over-wifi requires, such as DNS-SD. One option is to re-implement everything that connectedhomeip's DNS-SD does: advertising `_matterc._udp` records for on-network commissioning, advertising `_matter._tcp` records so the Matter controller can discover the device, and discovering other Matter devices. But that takes a lot of effort and becomes very fragile (upgrading to a new connectedhomeip version would probably require a full rewrite).

Another solution is to enable Ethernet in connectedhomeip. Ethernet requires the same DNS-SD implementation as WiFi does, but unlike WiFi it doesn't conflict with ESPHome's WiFi driver. This is the solution that `esphome-matter` currently uses.

The Ethernet approach works as follows. Setting `CONFIG_ENABLE_ETHERNET_TELEMETRY=y` makes connectedhomeip think it has an Ethernet interface, which keeps DNS-SD and operational discovery enabled. Since there's no real Ethernet hardware, the actual hardware init functions (`ConnectivityManagerImpl::InitEthernet()` and `ESPEthernetDriver::Init()`) are replaced with no-ops defined in `matter_ethernet_stub.cpp`. These override the archive members at link time because object files take precedence over static library members.

This approach is still somewhat fragile. Two of connectedhomeip's source files (`NetworkCommissioningDriver_Ethernet.cpp` and `ConnectivityManagerImpl_Ethernet.cpp`) reference Ethernet hardware types that don't exist on targets without a built-in MAC (ESP32-C3, C6, etc.). These files must be excluded from the build entirely, which is done in the project-level `CMakeLists.txt` via `idf_component_get_property` and `set_target_properties` after `project()`. Similarly, `ESP32DnssdImpl.cpp` is excluded by esp-matter when both `ENABLE_WIFI_STATION=n` and `ENABLE_WIFI_AP=n`, but since ESPHome manages WiFi the ESP mDNS library is still available. So that file has to be added back using `target_sources`. Any of these exclusions or additions could silently break when upgrading esp-matter or connectedhomeip.
